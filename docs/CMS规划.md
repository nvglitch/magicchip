# MagicChip 网站 CMS 建设规划

编写日期：2026-09-09  
依据：当前工作区的网站源码、内容文件和配置；CMS 能力参考官方文档。本文是实施规划，尚未安装后台、迁移数据或变更网站功能，也未核验线上部署环境。

## 1. 建议结论

保留现有 Next.js 网站和页面设计，增加一个管理结构化内容的 CMS。先统一产品数据，再让后台接管内容；产品列表、详情、搜索、SEO 和场景推荐共同读取同一份已发布数据。

推荐组合：**独立部署 Payload CMS + PostgreSQL + 对象存储，现有 Next.js 通过服务端内容接口接入**。后台界面可以用中文，前台继续以英文为默认语言，兼容现有法、德、意、西四种语言。

第一版解决六件事：

1. 运营能够新增、修改、排序和上下架产品，无须同步修改多份代码。
2. 图片、产品手册和下载资料有统一资源库，并能关联产品。
3. 新闻有真实正文，支持草稿、预览、审核和发布。
4. 全站联系方式、首页轮播和推荐产品可以统一维护。
5. 询盘真实保存，销售能够查看和跟进。
6. 内容发布后，页面、搜索和 SEO 在约定时间内同步更新。

不把自由拖拽建站、电商交易、库存、复杂报价系统和完整 CRM 放进第一版。现有网站的核心业务是 B2B 产品展示与获取询盘。

## 2. 当前实现与问题定位

### 2.1 技术基础

- `package.json` 声明 Next.js 16.1.6、React 18.3.1、TypeScript、Tailwind CSS 4 和 Framer Motion。
- 首页、新闻等部分内容由 `lib/content-loader.ts` 使用文件系统读取 JSON。
- 产品页、公司页、工厂页等大量内容仍保存在客户端页面组件或 TypeScript 目录文件中。
- 在本次检查的应用源码和依赖中，未发现已接入的 CMS、数据库或实际询盘提交接口。
- 未发现足以确定线上托管方式的部署配置，因此不能假定现有主机能够持久写入文件或运行数据库。

### 2.2 内容来源清单

| 内容 | 当前主要来源 | CMS 处理方式 |
| --- | --- | --- |
| 首页轮播 | `content/banners/*.json` → `app/page.tsx` → `HeroBanner` | 迁移为轮播集合，支持排序、图片、链接及发布状态 |
| 首页分类 | `content/products/*.json` → `getAllProducts()` | 实际是分类数据，重命名为 ProductCategory，避免与单个产品混淆 |
| 分类产品列表 | `app/products/[category]/page.tsx`，三个 catalog 文件及部分 `sampleProducts` | 从统一 Product 查询，按分类、系列、排序字段展示 |
| 产品详情 | `app/products/[category]/[id]/page.tsx`：目录转换结果与型号专用覆盖数据 | 导入最终生效数据，保留完整画廊、优势及卖点内容 |
| 产品 JSON 副本 | `content/products/items/*.json` | 仅作为核对来源；当前并非完整有效的产品主库 |
| 防火墙规格 | `lib/firewall-catalog.ts` 与 `lib/firewall-brochure-specs.ts` | 保留手册规格覆盖优先级，并记录参数依据 |
| 搜索 | `lib/site-search.ts`：目录生成条目 + 人工条目 | 从已发布内容生成统一搜索索引，支持运营补充关键词 |
| SEO、产品路径 | `lib/seo.ts`、产品 layout、`app/sitemap.ts` | 使用统一产品、分类与新闻数据生成 |
| 新闻 | `content/news/*.json` + `app/news/[id]/NewsArticleClient.tsx` | 增加正文、作者、SEO、关联产品；移除占位正文 |
| 首页推荐产品 | `components/FeaturedProduct.tsx` | 首页配置关联 Product，避免写死型号与图片 |
| 公司、关于、工厂、服务、实力展示 | 对应页面和 `Services`、`SocialProof` 等组件内文案或翻译键 | 用固定页面模板及结构化内容字段管理 |
| 应用场景 | `app/scenarios/page.tsx` 的场景数组、推荐型号和多语言文案 | Scenario 关联多个产品，产品名称与路径自动读取 |
| 联系方式、导航和页脚 | `content/site-config.json` 与各组件硬编码并存 | 统一 SiteSettings 和 Navigation；所有入口读取它们 |
| 文档入口 | `app/documents/page.tsx` | 保留为资源中心入口，链接到统一资料库和新闻 |
| 下载与技术资料 | `/downloads` 是编辑中占位页；`/tech-docs` 的下载链接存在 `href="#"` | 建立 Resource 集合，只有真实文件通过检查后才能发布 |
| 询盘 | 首页 ContactSection、联系页、LiveChatWidget 等 | 接真实服务端提交、持久化、通知与后台跟进 |
| 多语言 | `lib/i18n/LanguageContext.tsx`、`locales/*.ts`、页面对象及 JSON | UI 字典与业务内容分离；业务内容交给 CMS |

## 3. 技术选型与部署

### 3.1 选型建议

| 方案 | 对本项目的判断 | 建议 |
| --- | --- | --- |
| Git/JSON 内容管理 | 可延续现有文件，但复杂产品关系、文件版本、权限及询盘需要另外建设；发布通常还需构建 | 可作过渡导出格式，不作为长期主方案 |
| Payload CMS | 适合由现有 TypeScript 团队定义产品结构、关系和后台扩展 | 推荐，先独立部署 |
| Strapi | 提供内容类型、内容管理、多语言和 API；若团队已有经验，可减少学习成本 | 备选，不能仅为 CMS 再引入两套后台 |
| 完全自研后台 | 编辑器、登录、权限、文件、版本和审计均需维护 | 当前投入收益不合适 |

Payload 官方提供字段级多语言、草稿能力、PostgreSQL 适配器和对象存储适配器，可作为本方案基础。审核分工、参数核验、询盘跟进和跨系统发布状态仍需项目配置或定制，不能假设安装后自动具备完整业务流程。参考：[多语言](https://payloadcms.com/docs/configuration/localization)、[草稿](https://payloadcms.com/docs/versions/drafts)、[PostgreSQL](https://payloadcms.com/docs/database/postgres)、[存储适配器](https://payloadcms.com/docs/upload/storage-adapters)。Strapi 的能力参考其[官方文档](https://docs.strapi.io/)。

### 3.2 为什么第一版独立部署

核验时 Payload 官方安装文档列出的 Next.js 支持范围包括 15.2.9–15.2.x、15.3.9–15.3.x、15.4.11–15.4.x 和 16.2.6+，当前项目的 16.1.6 不在该范围内。不能直接承诺将最新版 Payload 装入现有应用即可工作。具体版本在实施时锁定并复核，参见[安装要求](https://payloadcms.com/docs/getting-started/installation)。

因此建议 CMS 独立应用、独立依赖和部署，官网保留现有前端，通过服务端 API 连接。未来如果需要合并部署，再单独评估 Next.js、React、现有动画和地图组件的升级兼容性。

### 3.3 数据与访问路径

```text
运营 / 产品负责人 / 销售
             ↓ 登录
      CMS 后台与受保护 API
          ↙          ↘
 PostgreSQL       对象存储：图片、PDF、下载文件
       ↓ 已发布内容       ↓ CDN
 Next.js 服务端内容层 → 现有页面模板 → 网站访客
       ↑
 CMS 发布事件 → 验签 / 重试 → 页面与搜索缓存更新

访客询盘 → 官网服务端接口 → 询盘持久化 → 通知队列 → 销售
```

官网浏览器不持有 CMS 管理密钥，也不直接查询询盘表。公开内容响应只包含已发布、允许公开的字段。后台、数据库和对象存储需要分别备份；开发、预发布和生产环境使用独立数据与凭据。

## 4. CMS 管理边界与菜单

后台建议提供：产品管理、分类与系列、媒体库、资料中心、新闻管理、首页管理、页面内容、应用场景、站点设置、询盘管理、发布记录、用户权限。

**运营可管理：** 文案、型号、参数、图片、资料关联、推荐关系、展示顺序、SEO、联系方式和内容状态。

**开发继续管理：** 页面布局、断点、动画、交互逻辑、组件代码、参数派生规则、访问权限及发布校验。颜色和图标可给有限预设选项，不开放任意 Tailwind 类名、脚本或组件代码。

首页采用固定区块：首页轮播 → 分类 → 推荐产品 → 服务 → 实力展示 → 联系入口。后台可编辑区块内容与允许的显隐设置；第一版不建设自由拖拽页面编辑器。

## 5. 内容模型设计

所有可发布内容统一记录 `id`、`status`、`createdAt`、`updatedAt`、`publishedAt`、`revision`、`updatedBy`。状态至少包含草稿、待审核、已发布、已归档；CMS 自带发布状态与业务审核状态分开实现，只有审核通过的版本可对外发布。

### 5.1 ProductCategory / ProductSeries

分类包含 `slug`、多语言名称及描述、分类图、主题预设、排序、SEO、启用状态。系列关联唯一分类，包含稳定 `code`、标题、介绍、图片和排序。

保留现有 `#series-a`、`#series-1u` 等分类页锚点。产品分类和系列必须匹配；有产品引用的分类或系列不能直接删除，应先迁移引用或归档。

### 5.2 Product：第一版的核心模型

| 字段组 | 建议字段 | 规则 |
| --- | --- | --- |
| 身份 | `id`、`slug`、`model`、`category`、`series`、`order` | 内部 ID 不变；现有 slug 保留；slug 全局唯一以兼容当前按 ID 查找方式 |
| 文案 | `tagline`、`description`、`highlights[]` | 业务文本支持多语言；英文必填 |
| 列表卡片 | `cardImage`、`cardHighlights[]` | 默认读取主图和核心亮点，允许人工覆盖；仍保存在同一产品内 |
| 主图区 | `heroImages[]` | 引用媒体记录，支持顺序和受控留白预设 |
| 产品画廊 | `galleryCards[{media,title,description}]` | 保留现有图片说明和顺序，不丢弃型号专属内容 |
| 参数 | `specGroups[{title,rows[]}]` | 每行含稳定 key、标签、值、单位、排序及适用配置备注 |
| 优势 | `features[{iconKey,title,description}]`、`advantageSummary` | 图标仅能从白名单选择 |
| 卖点图 | `sellingPoints[{media,title,description}]` | 与方图画廊分开编辑和呈现 |
| 工作环境 | `operatingRange` | 初期保留准确文本；结构化温度值需经人工核验 |
| 关联 | `resources[]`、`relatedProducts[]`、`scenarioIds[]` | 只选择现有记录，链接由系统生成 |
| SEO | `seoTitle`、`seoDescription`、`ogImage`、`noIndex` | 默认从产品信息派生，支持运营覆盖 |
| 参数依据 | `specSource`、`sourceVersion`、`sourcePage`、`verifiedBy`、`verifiedAt` | 后台可见，避免将内部备注公开 |
| 生命周期 | `availability`、`replacementProduct` | 可选在售、询价、停产；不要与草稿发布状态混用 |

产品详情继续使用现有顺序：主图区、画廊、规格矩阵、优势、卖点图、询盘入口。是否显示某个可选区块由内容是否完整决定。

现有 `specs`、JSON 中的 `specifications` 和手册覆盖参数统一映射到规格行。CPU、网口数量、内存、尺寸等不全部塞入富文本；第一版不强行把所有自由文本自动拆成数字。需要筛选的参数以后增加经过核验的结构化字段，展示参数仍保留原始语义与配置条件。

系列优势可以作为创建产品时的模板，复制后存入产品版本，避免后续修改系列介绍使全部已发布产品未经审核改变。`compactCatalogHighlights` 等规则可提供初始建议值，最终由运营检查后保存。

### 5.3 Media / Resource

Media 管物理文件：存储 key、原文件名、文件类型、大小、宽高、哈希、多语言 alt、内部备注和引用关系。图库角色如主图、画廊、卖点图放在产品引用处，同一文件可以被多个位置使用。

Resource 管业务资料：标题、类型、文件、语言、版本、发布日期、关联产品、说明、公开范围、状态。类型包括手册、规格书、驱动、固件、证书和营销资料；只有确实有文件的类型才展示。

处理规则：

- 图片与 PDF 统一上传到持久对象存储，不能依赖应用临时磁盘或在线写回 `public/`。
- 存量 `/assets/...` 路径先保持可用，建立旧路径到媒体 ID 的映射后再迁移。
- 文件替换生成新版本或新存储 key，不覆盖已被缓存的文件；保留旧版本引用用于回滚。
- 删除前检查产品、页面、新闻和历史版本引用，优先归档。
- 产品技术图默认完整显示，轮播背景可裁切；CMS 提示尺寸比例，前台模板执行展示规则。
- 私有资料使用受保护下载接口和短时授权链接，不能只隐藏页面入口却保留公开文件 URL。
- 第一版资料默认公开下载；留资下载作为后续可选功能。

特别注意：当前 `.gitignore` 忽略 `*.pdf`。迁移前需单独盘点本地手册与线上实际可用文件，Git 仓库不能被视为资料备份的完整来源。

### 5.4 NewsArticle

包含稳定 slug、多语言标题、摘要、正文、封面、分类、作者、发布日期、关联产品和 SEO。正文采用受控富文本，支持标题、段落、列表、图片、表格和链接；不允许任意脚本或未过滤 HTML。

现有三篇 JSON 新闻可以导入草稿。正文尚未提供时，明确标记待补充，不把摘要或占位文字当作完整文章发布。既有已公开地址的处理需结合线上状态决定：补正文后继续使用原地址，或明确归档；不能静默批量删除。

### 5.5 全局设置与固定页面

| 模型 | 内容 |
| --- | --- |
| SiteSettings（单例） | 公司名称、Logo、邮箱、电话、WhatsApp、地址、营业时间、社交链接、默认 SEO |
| HomePage（单例） | 轮播引用、分类顺序、推荐产品引用、服务与实力展示内容 |
| Banner | 桌面图、可选移动图、标题、副标题、按钮文字、目标链接、顺序和状态 |
| Navigation（单例） | 导航、下拉推荐、页脚分组；内部链接选择内容记录，外链单独校验 |
| CompanyProfile（单例） | 公司介绍、成立年份、团队和生产数据、认证及资料依据；供 about/company 复用 |
| FactoryPage（单例） | 工厂介绍、照片、生产流程、设备、质量控制、产能数据 |
| Scenario | 稳定标识、多语言标题和文案、图片、推荐产品及排序 |

公司成立年份可用于计算经营年限；产能、人员、认证等事实字段记录更新时间和审核人，防止不同页面出现不一致说法。

### 5.6 Inquiry：独立业务集合

字段包括姓名、邮箱、公司、询盘类型、关联产品 ID、提交时型号快照、数量、留言、来源页面、语言、创建时间、负责人、跟进状态、内部备注和通知状态。型号快照用于保留客户提交当时的背景。

统一流程：前台校验 → 服务端再次校验与限流 → 保存询盘 → 返回成功 → 异步通知销售。通知失败不丢失询盘，支持重试；保存失败必须告知用户并保留输入。通过提交标识避免重复点击造成重复记录。

首页表单、联系页和悬浮留言使用同一提交接口。产品询盘按钮携带产品 ID；服务端验证关联存在，不能完全信任浏览器传入型号。邮箱和通知凭据仅保存在服务端。

询盘不进入公开内容 API、搜索、站点地图或页面缓存。销售仅访问获授权的询盘；导出和删除需要权限并留操作记录。保存期限及隐私告知由业务确定后配置。

## 6. 多语言策略

当前启用 `en`、`fr`、`de`、`it`、`es`；`zh` 只是部分内容中的可选字段，不代表前台已支持中文。后台中文界面不等于新增中文站。

按钮、错误提示、菜单通用词等 UI 字典继续留在 `lib/i18n/locales/`；产品、新闻、分类、页面营销文案和 SEO 进入 CMS 的本地化字段。

英文为内容源语言，非英文缺失时先回退英文。型号、slug、媒体关系和硬件数值跨语言共享，标签和解释性文字可翻译；不同语言版本手册分别建 Resource。自动翻译结果为待审核，不直接发布；源文更新时将相关译文标记为待复核，具体审核与过期提示需要定制。

第一阶段保留现有浏览器语言切换，避免 CMS 迁移同时改全部 URL；服务端至少输出完整英文内容，客户端切换只能读取已发布译文。

现有语言选择依赖 localStorage 和客户端 Context，不能据此认为五种语言都已经拥有可独立索引的 SEO 页面。若海外自然搜索是重点，第二阶段建设 `/fr/...`、`/de/...` 等语言路由，并同步服务端语言内容、metadata、canonical、hreflang 和 sitemap。默认英文 URL 尽量保留；只有真正可访问、准备好的语言页面才输出对应 SEO 链接。

## 7. 前端接入与发布机制

### 7.1 统一内容接口

建议新增 `lib/cms/`，提供带类型和运行时校验的服务端读取层：

```text
getCategories(locale)
getProducts({ category, series, locale, page })
getProductBySlug(categorySlug, productSlug, locale)
getNewsList(locale) / getNewsBySlug(slug, locale)
getResources({ productId, type, locale })
getSiteSettings(locale) / getHomePage(locale)
getPublishedRoutes() / getSearchEntries(locale)
```

这些是拟建接口，不是当前已有实现。公开读取默认只允许已发布版本；预览走独立鉴权通道。

将产品路由改为服务端获取当前产品或当前分类内容，再把必要数据传给动画、筛选、语言切换和灯箱等客户端组件。不要把整个产品目录、后台 SDK 和管理凭据打进浏览器包。

页面正文、`generateMetadata` 和结构化数据使用同一产品读取逻辑；分类不匹配、内容未发布或不存在时由服务端返回正确状态。搜索索引由产品、分类、场景、资源和新闻的已发布记录生成，不再单独维护重复型号文案。

### 7.2 发布与缓存

发布后触发 CMS 事件，经签名验证后刷新对应内容缓存。必须配置缓存标记及真实读取链路，不能仅增加一个 webhook 就认为所有页面都会更新。

| 变更 | 需要同步的范围 |
| --- | --- |
| 产品 | 产品页、所属分类、首页推荐、关联场景、关联资料、搜索、SEO、sitemap |
| 分类或系列 | 分类导航、分类页、产品面包屑、搜索；地址变化时含旧地址 |
| 新闻 | 新闻列表、详情、资源中心相关入口、搜索、sitemap |
| 联系方式 | 首页、导航、页脚、联系页、悬浮入口及组织结构化数据 |
| 媒体或资料 | 使用该资源的页面、资料列表及搜索 |

Next.js 的 `revalidateTag` 支持按标记失效；使用 `max` 配置时采用先返回旧内容再后台刷新的语义，不等于发布瞬间所有访问都读到新版本。实现须与项目锁定版本一致，参见[官方说明](https://nextjs.org/docs/app/api-reference/functions/revalidateTag)。

建议验收目标：普通发布 60 秒内在新请求中可见；下架内容在约定时限内从详情、搜索和站点地图移除，并单独验证缓存及 CDN 行为。已经打开的浏览器页面默认需刷新，不承诺实时推送。

增加发布任务记录、幂等事件 ID、失败重试和“重新同步”操作。内容保存成功与前台同步成功分别显示。CMS 暂时不可用时，可服务最后一次已发布缓存；没有缓存时返回可识别错误，不能像当前 JSON 读取失败那样直接转为空列表并让站点看起来正常。迁移完成后不自动回退到旧源码数据，避免下架产品被重新展示。

### 7.3 预览与地址管理

编辑员通过登录态或短时签名链接预览草稿，预览关闭公共缓存并设置 noindex；普通访客无法用 `draft=true` 之类参数绕过权限。

默认保留所有有效分类、产品和新闻 URL。确需修改 slug 或分类路径时，建立 Redirect 记录并更新引用、canonical、sitemap 和缓存，检查重定向循环。永久迁移用 301/308；停产但仍有支持价值的产品可保留页面并推荐替代型号，完全撤销的内容根据业务决定 404/410，避免全部跳回首页。

## 8. 权限与日常操作

| 角色 | 权限 |
| --- | --- |
| 管理员 | 账号、权限、站点设置、配置和恢复 |
| 内容编辑 | 编辑产品、页面和新闻草稿，管理获授权媒体，提交审核 |
| 产品审核 / 发布负责人 | 核验规格与手册，批准发布、下架与版本恢复 |
| 翻译人员 | 编辑指定语言文案；不能修改型号事实或直接发布 |
| 销售 | 查看获授权询盘、分配及跟进；不默认拥有内容发布权限 |

小团队可以让同一人兼任多角色，但权限仍在服务端检查。除了后台按钮，API、文件上传和批量操作也要遵循相同权限。

产品发布前检查：分类和 slug 正确、英文内容齐全、主图存在、规格有依据、图注与图片一致、资料链接有效、关联记录可见、SEO 可用。草稿可不完整，发布不能绕过这些检查。

版本恢复生成新的待审核版本，再经发布同步到官网；记录谁改了哪些内容、谁发布以及对应版本。文件上传限制类型和大小，富文本链接做安全处理。

## 9. 迁移方法与数据优先级

### 9.1 先生成网站当前有效内容快照

迁移对象是“最终生效内容”，不只是 `content/` 目录。建立按产品 ID 汇总的清单，记录分类、系列、列表内容、详情、SEO、搜索条目、媒体、资料以及各字段来源。

产品合并遵循：

1. 以三个 catalog 的运行时结果和页面专用型号记录构建候选集合。
2. 防火墙目录已使用 `firewallBrochureSpecs[input.id] ?? specs`；导入时必须执行等价合并，不能丢掉手册覆盖值。
3. 详情页的 `products` 在目录展开后又定义部分型号，后定义数据生效；画廊、卖点、规格和简介按实际最终结果提取。
4. 列表专用摘要及详情专用描述分别保留；同一事实冲突时输出差异报告，由产品负责人核验，不能机械指定页面永远正确。
5. `content/products/items/` 中的字段和旧资源路径只作比对，不直接覆盖当前页面。
6. 系列说明、画廊路径推导、搜索人工关键词、SEO 覆盖及场景推荐都需要显式迁移；不能只导出 catalog 原始数组。

例如 MCIPCB12 的 JSON 图片路径与当前详情使用的系列目录不同，说明文件副本存在漂移。迁移工具应检查文件存在性、URL 可用性和对应实物内容，不能仅检查 JSON 是否能解析。

### 9.2 导入与切换

按“媒体 → 分类/系列 → 产品 → 资料关联 → 新闻 → 页面/场景/导航 → 全局设置”导入。交叉关联可在第二遍按稳定 ID 回填。

导入脚本支持试运行、重复执行不重复建记录、错误报告及旧 ID 映射。先导入隔离测试环境，核对产品唯一数、路由集合、规格、图片顺序、资料、搜索与 SEO。差异必须有解释，不能只比较条数。

随后让预发布官网只读取 CMS，与旧站逐页抽查。正式切换安排短暂内容冻结，备份旧站与新数据库，核对最终增量，然后开启 CMS 编辑入口。每个模块切换后明确唯一可写来源，不长期双向写 JSON 与数据库。

回滚准备包括前端部署版本、数据库备份、资源版本及切换后新增内容导出；询盘单独保护，不能通过回滚内容库覆盖新增客户记录。确认稳定后才删除旧页面数据、catalog 副本和手工 SEO/搜索条目，并更新 README 的维护说明。

## 10. 分阶段执行与投入估算

以下为一名熟悉本项目的全栈开发者、内容负责人能及时参与核验时的初步人日估算，不是报价或交付承诺。全量人工翻译、规格考证及补写内容另计。

| 阶段 | 主要交付 | 估算 | 验收条件 |
| --- | --- | --- | --- |
| P0：盘点与验证 | 内容快照、冲突清单、CMS 独立部署验证、一个完整产品样例 | 2–4 人日 | 从后台编辑样例到预发布页面、权限及文件持久化跑通 |
| P1：后台基础 | 数据库、媒体、用户、分类/系列、产品、站点设置、草稿预览 | 4–7 人日 | 运营能够维护真实产品并保存/预览草稿 |
| P2：核心迁移 | 全量产品导入、列表详情接入、导航与联系方式统一、搜索/SEO/发布同步 | 5–8 人日 | 一个产品变更在所有关联入口一致生效，原有效 URL 保持可用 |
| P3：业务闭环 | 新闻正文、真实资料下载、询盘入库通知及跟进、首页运营配置 | 4–6 人日 | 能完成产品发布、资料下载、客户询盘和销售查看 |
| P4：上线收尾 | 权限和发布失败验证、备份恢复演练、页面检查、培训与操作说明 | 2–4 人日 | 回滚可执行，正式环境配置和数据验证通过 |

第一版合计约 **17–29 人日**，通常需预留约 4–6 周日历时间及内容核验缓冲。公司/工厂/场景的全面后台化、完整多语言 SEO 路由和高级筛选可在核心闭环稳定后继续。

如果必须压缩范围，先交付产品、媒体、联系方式与询盘；新闻和下载在资料尚未就绪时明确显示可用内容或暂时隐藏对应入口，不能保留“看似成功”的假提交和空下载按钮。

运行成本需按供应商实际报价确认，包括 CMS 应用、数据库、对象存储与流量、备份、邮件服务及监控。预算尚未提供，不在此假定免费托管能够满足长期运营。

## 11. 上线验收清单

- [ ] 后台新增一个产品后，无须改源码即可出现在正确分类、系列、详情、搜索及 sitemap。
- [ ] 修改产品文案后，正文、metadata、结构化数据以及首页/场景引用同步一致。
- [ ] 修改电话或 WhatsApp 后，导航、页脚、首页、联系页和悬浮入口全部一致。
- [ ] 核对工业、AI、商用、防火墙各类样本，并包含 TPC、NAS、1U、定制画廊和横向卖点图。
- [ ] 草稿及未审核内容无法被匿名 API、搜索、页面缓存或 sitemap 读取。
- [ ] 非英文缺失有确定回退；已有译文能展示；源文更新后有待复核提示。
- [ ] 新闻展示真实正文；下载按钮返回真实文件；不存在仍指向 `#` 的有效下载入口。
- [ ] 提交询盘后后台有记录；邮件失败可重试；保存失败不显示成功；重复点击不会重复建单。
- [ ] 下架、改地址、资源替换和恢复版本均经过端到端检查。
- [ ] CMS 故障、发布通知失败、数据库不可用时均有明确行为及恢复路径。
- [ ] 数据库、文件和配置备份已实际恢复验证；应用重新部署后上传文件仍存在。
- [ ] 代码接入完成后执行生产构建、适当的权限/API/发布集成测试，并检查桌面和移动页面。

## 12. 实施前需要落实的条件

默认按“小团队运营、自持数据、英文优先、保留现有前台设计”推进技术验证。正式部署前需落实官网当前托管环境、CMS 与数据库预算、运营及发布负责人、询盘收件邮箱、文件规模和多语言 SEO 优先级。

建议首先拿三个样例验证模型：一个含复杂画廊的工业型号、一个使用手册规格覆盖的防火墙型号、一个 URL 与型号名称不同的 AI 型号。样例完成后台编辑、预览、发布、搜索与 SEO 同步后，再批量迁移全站。
